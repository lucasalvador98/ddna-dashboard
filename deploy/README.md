# Reviewed CI/CD proposal — dashboard

**Prepared, not installed or activated.** No production deploy/rollback is part of this PR. Original repo working trees are preserved through isolated worktrees. Pipeline:

`PR → CI (all checks required) → main push CI success → GHCR image by full SHA/digest → manual dispatch on main → component-only deploy → readiness → automatic image rollback on failure`.

## Workflows and trust boundaries

- `ci.yml`: pull_request + push main; no production secrets, no environments or SSH. Final required check `Validate dashboard` is green only if every job is green. No continue-on-error, exclusions, weakened lint, baseline suppression or secret-bearing PR builds.
- `publish.yml`: workflow_run of successful **push/main CI only**, same repository. It never consumes PR artifacts or PR code. Check out the validated head_sha and build `linux/amd64` for the VPS. Publish `ghcr.io/lucasalvador98/ddna-dashboard:<full-SHA>`; registry digests are immutable, tags identify the revision and can be rebuilt. Metadata/digest retained as an artifact for 90 days. No `latest`, no deploy trigger.
- `deploy.yml`: only workflow_dispatch on main, selected SHA must be **current main tip**, latest CI and publication runs for that SHA must succeed. Deploy by GHCR digest. Per-repo concurrency never cancels a production release; shared VPS flock also serializes the two repositories (60s lock timeout), revalidates main after locking and after pulling, and refuses stale/out-of-order dispatches.
- Minimum token permissions: contents read everywhere; packages write only publication, packages read and actions read only deployment. No repo PAT needed for builds. VPS pulls using the short-lived job GITHUB_TOKEN sent over restricted SSH stdin, deleted from temporary Docker config immediately; it is never persisted/logged. Publication access to a pre-existing private GHCR package still depends on its Actions repository permissions.
- Dedicated SSH key per component, existing host ED25519 pin in `deploy/known_hosts`; user deploy / 179.199.132.207 / TCP22. No ssh-keyscan trust-on-first-use, shared personal key, runner installation or firewall changes.

## Receiver and rollback protections

`deploy/host/deploy.py`, `healthcheck.py`, `rollback.py`, `archive.py`, `policy.py` are the reviewed replacement for the legacy receiver. Both repositories contain byte-identical copies; install once. Existing restricted keys are reused, without creation/rotation. The installer updates only their forced command paths to root-owned `/usr/local/lib/ddna-cicd/deploy.py`; it never runs Docker or restarts anything.

Services are fixed: wordpress → ddna-wordpress-app; dashboard → ddna-observatorio-candidate. Use only the three active infrastructure Compose files plus a generated per-component override which pins **both currently running image IDs**, avoiding stale permanent/legacy release references. The only mutating Compose command is `up -d --no-deps --no-build --pull never <selected component>`. No checkout/pull in VPS application repos, DB import, editorial operation, upload sync or infrastructure deploy.

Before recreation: 4 GiB free minimum plus sufficient space for a previous-image archive; validate image source/revision/amd64, main/checks, configured environment drift. After: mounts, networks, ports and application env stay identical; every other running container keeps ID/image/StartedAt, including MariaDB, all Supabase services, PostgreSQL, Caddy and the other frontend.

Health budget: 150s, HTTP timeout 8s/request, polling 2s. WordPress requires container healthy, Home/theme and wp-login; Dashboard requires container healthy, /observatorio/, /observatorio/login, /observatorio/api/health with Supabase **connected**. Stale categories with connected backend are accepted and reported separately; HTTP200 alone is insufficient. A sibling/backend problem does not trigger WordPress rollback. Requests use the remaining readiness budget; workflow max35min, sender SSH max1800s. Image save and compression are separately bounded to180s each. Single-instance recreation has brief interruption; zero downtime is not promised.

On failure/interruption, rollback ONLY selected previous image, healthcheck again; `rollback-failed` requires operator and fails Actions. JSON records in `/home/deploy/ddna-infra/cicd/v2-state/` include SHA, GHCR digest, previous ID/revision, archive and status, never credentials. Registry auth directory and runner SSH key are removed. SIGTERM/SIGHUP handled; SIGKILL/host failure cannot run automatic rollback: inspect log and use the exact previous ID. Images are never pruned by this pipeline.

**Existing cron interference:** `/home/deploy/scripts/maintenance.sh` performs weekly prune, including `-af` if disk >80%. Durable app-image `docker save`+gzip checkpoints (0600) are created before recreation, checksum checked on restore; rollback reloads one if cron removed the old image. This is code-image backup only, not DB/uploads. No retention cleanup is automatic; an administrator approves archive retention/disk housekeeping separately. Daily existing backup is PostgreSQL, not proof of a current MariaDB backup.
